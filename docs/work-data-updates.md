## 3. フィールドと表示の関係

### 現在のデータに存在するフィールド

全69件に`id`・`title`・`status`・`category`・`series`・`world`・`position`・`mainCharacter`・`relation`・`cover`・`coverStatus`・`isNew`・`tags`・`description`・`platformClassifications`がある。

一部に`releaseDate`・`catchphrase`・`zetaUrl`・`chachaUrl`・`zeta`・`url`・`link`・`archiveOnly`がある。未登録値を推測で埋めない。`relation`には人物名や関係の説明があり、関連作品ID配列とは扱いが異なる。

| 内容 | 実装上のルール・注意 |
| --- | --- |
| 作品の同一性 | `id`が詳細表示・シリーズ所属等のキー。タイトル変更でIDを変更しない |
| 掲載状態 | `status === 'published'`かつ`publicationStatus !== 'private'`が表示条件。外部サービス上の現在の公開状態を保証する値ではない |
| アーカイブ | `archiveOnly`または`archiveStatus === 'archived'`で判定。現在4件は`archiveOnly: true`で、`status: published`のまま収録 |
| 公開先分類 | `platformClassifications[].platform`。`zeta` / `chacha` / `talelynx`。フィルターはURLではなくこの分類を見る |
| 分類来歴 | `source`・`sourceFile`・`sourceField`・`note`等を維持。`currentPublicationStatus: unverified`も現在の状態確認済みを意味しない |
| 公開先URL | 複数の旧形式を`eternoa.js`が収集して重複を除く。実ホスト名でリンクのプラットフォームを判定。キー名だけを根拠にURLを移し替えない |
| リンク利用可否 | `linkAvailability[platform]`に対応。未指定時は通常`listed`、アーカイブ`unknown`。`unavailable`ならリンクを出さない。分類・掲載・アーカイブとは別 |
| 初公開日 | `firstPublishedAt || releaseDate`。現在は一部の`releaseDate`を使用。`YYYY-MM-DD`または`YYYY.MM.DD`で認識 |
| 更新・移植日 | `updatedAt || updateDate`、`transferredAt || transferDate`を表示できるが、現行69件にはこれらの専用フィールドはない。新規に記録する際は事実の裏付けと仕様確認が必要 |
| シリーズ所属 | `series[].works`のID一覧に加え、作品の`series`または`world`とシリーズIDの一致で判定。既存の文字列ラベルを無条件にIDへ置換しない |
| ジャンル | `categories`から選択肢と表示名を取得。フィルターは作品の`category`・`world`・`series`との一致を判定 |
| 関連作品 | 明示的な`relatedWorks`または`relatedWorkIds`と同一シリーズ所属から生成。現行データに明示的な関連IDフィールドはなく、主にシリーズ所属から表示 |

`publicationStatus`・`archiveStatus`・`linkAvailability`・`firstPublishedAt`・更新/移植日・明示的な関連作品ID・`platformLinks`・`talelynxUrl`は、実装が受け入れる形式だが現在の作品データにはない。既に登録されていると説明したり、未確認値を自動追加したりしない。

### 自動で変わる表示とHTMLの例外

- WORKS一覧・検索・詳細は`catalogue.js`を使用。検索対象はタイトル・紹介文・主な人物・シリーズ表示名・ジャンル名・タグ。HTMLの紹介文を別に複製しない。
- HOMEのLATEST RELEASEは初公開日順の表示作品から、非アーカイブかつ利用不可扱いでない登録リンクを持つ作品を選ぶ。URL未登録作品がZETAフィルターに出ても、LATESTに選ばれるとは限らない。
- RECENT ADDITIONSは初公開日順で、LATESTに選ばれた作品を除く3件。専用の追加日で並べているわけではない。初公開日を追加日・移植日に書き換えて順位を操作しない。
- 更新順は初公開日・公開日・更新日・移植日の認識可能な値の最大を使う。日付未登録作品は末尾。`isNew`だけで順位は変わらない。
- EUPHORIA・東方妖界の作品一覧と件数はカタログから描画される。シリーズ本文はHTMLに残る。
- VELVET NIGHTには4枚の固定カードがあり、画像パスと作品カバーの一致から詳細表示へ接続する。シリーズのID一覧だけではカードは増えない。カードの人物名・作品名・alt・外部href・固定件数表記も確認する。新規作品やカバー変更時は、別途承認されたHTML変更が必要になる場合がある。
- WORLDの世界観説明・リンク、各ページのtitle/description/OG/canonicalはHTML。作品タイトル変更だけでこれらが自動更新されるわけではない。

紹介文の改行は文字列内の改行として保存し、`eternoa.js`がテキストとしてエスケープして表示する。詳細とHOME要約は既存CSSの改行表示を使用する。`<br>`や`<p>`を紹介文へ埋め込まない。JSON形式の文字列では改行を`\n`として正しくエスケープし、画面に文字として「\n」が出る二重エスケープを避ける。原稿の文言・段落を無断で整形しない。

## 4. 更新種別ごとの変更範囲

| 操作 | 原則として更新する場所 | 追加確認する場所・リスク |
| --- | --- | --- |
| タイトル・紹介文の修正 | 対象IDの`works`内フィールドのみ | 作品名を記載した固定HTML、VELVETカード、過去NEWS。過去記事の文言は別承認なく変更しない |
| URLの追加・修正 | 対象のURLフィールド。分類変更を伴う場合のみ分類も承認に従う | 重複URL・ホスト・利用可否。分類をURLから勝手に再構成しない |
| 分類・シリーズ変更 | 対象作品、必要な`categories` / `series[].works` | WORLDからのクエリ、各シリーズ一覧・関連作品、選択肢の互換性 |
| アーカイブ化・リンク停止 | 確認済みの状態フィールドを最小限更新 | アーカイブは削除しない。リンク停止を理由に分類や初公開日を消さない |
| 新規作品追加 | 一意なIDの作品レコード、承認済み画像、必要なシリーズ所属 | 総数・分類別期待件数、静的カード、HOME掲載順、関連作品。NEWSは別承認 |
| 掲載終了・削除 | 承認範囲に従い掲載レコードと関連参照を整理 | `series[].works`、他作品の関連ID、NEWSの`relatedWorkIds`、固定カード・リンク。画像削除は独立判断 |

非表示・アーカイブ・掲載データからの削除は別の操作。削除の代わりに`status`を変更するなどの代替判断を勝手にしない。過去NEWSを削除すると履歴が失われるため、関連リンクの扱いを所有者に確認する。画像は他用途・OG・外部直リンクの可能性があり、参照がなくなっただけで削除しない。

## 5. 作業の標準手順案

1. **範囲を確定**：作品ID、確定タイトル・本文、変更してよいフィールド、原資料、期待件数を記録する。追加・削除・分類変更がなければ69 / 56 / 21 / 0 / アーカイブ4を維持する。
2. **基準を保全**：最新mainのSHAと作業前データを記録し、mainから作業ブランチを作成する。3本の保全ブランチは更新しない。
3. **更新場所を照合**：`catalogue.js`の対象IDを一件だけ特定する。タイトル文字列だけで一括置換しない。固定HTML・NEWS・関連参照も検索する。
4. **承認された最小差分を作成**：暫定運用として現行カタログの対象フィールドを変更する。生成スクリプトが未確認のため旧入力から再生成しない。生成禁止コメントとの運用上の不整合は別途解消する。本書の採用だけではこの手順を実行しない。
5. **データを検証**：JavaScript構文、オブジェクト・配列の型、ID重複、追加削除ID、各作品の全フィールド差分を確認する。対象外の紹介文・タイトル・画像・分類・URL・日付の変更を0にする。
6. **参照を検証**：69件のカバー、シリーズID参照、関連作品ID、NEWSの関連ID、各HTMLにある対象作品へのリンクを確認する。カバー参照はルートHTMLからの相対パスとして解決する。URLのqueryを勝手に削除・置換しない。
7. **件数を検証**：実装と同じ掲載・分類・アーカイブ条件で集計する。通常/アーカイブ切替、ZETA URL未登録19件、複数分類を確認する。リンク本数とは比較しない。
8. **ローカル確認**：HTTPサーバーで全10ページを開き、検索・組合せフィルター・URL条件の保持、詳細・関連作品・スクロール復帰、NEWS、メニュー、ENTERを確認する。ファイルアプリのHTMLプレビューをブラウザ検証の代わりにしない。
9. **表示とビルドを確認**：320 / 390 / 768 / 1280px、実際のクリック・タップ相当の操作、改行・段落を確認する。GitHub Pages互換のJekyllでビルドし、必要ファイルと除外ファイルを照合する。新しい検証workflowが必要な場合は作業ブランチ限定・デプロイなしとし、本番反映対象に含めない。
10. **承認後に公開**：差分・検証結果・未確認項目を提示して停止する。公開が承認されたらmainの更新前SHAを再照合し、承認された差分だけ反映する。Pages設定は維持し、デプロイ後に公開URLを確認する。

テキスト更新時の件数確認だけで、本文23件の維持確認に代えない。全69件の本文・タイトルを更新前データと比較し、意図したIDとフィールドだけが変わっていることを確認する。

## 6. NEWS更新の独立手順

NEWSの項目は`id`・`publishedAt`・`category`・`title`・`body`・`status`・任意の`relatedWorkIds`・`externalUrl`。分類はRELEASE / UPDATE / TRANSFER / NOTICEを使う。掲載日は初公開日と別に記録する。

表示条件は`status: published`かつ掲載日が日本時間の当日以前。掲載日降順でHOMEには2件。未来日・非公開記事を「今すぐ公開済み」と扱わない。既存記事のIDや履歴を保持する。NEWS本文・タイトル中に作品名があっても、作品データのタイトル修正から過去記事を自動書換えしない。

## 7. 生成スクリプト調査と今後必要な仕様

`catalogue.js`の先頭は`// Generated by scripts/build-catalogue.mjs. Do not edit.`。しかしmainと3本の保全ブランチの先端に、該当スクリプト・`scripts/`・`package.json`は存在しない。同じパスについて、main・v8・旧Luno Worksの各先端を起点としたコミット履歴のAPI照会も0件だった。v8.1保全はmainと同じSHA。

これにより「確認したリポジトリとパス履歴には見つからない」と判断できるが、別名パス、削除済みで到達不能な履歴、別リポジトリ、作成者のローカル環境、未展開の保管ZIPまで不存在とは断定しない。保存文書の検索ではスクリプトの実体を特定できなかった。今回スクリプトを推測で再作成していない。

`sourceFiles`は22の由来ファイル名を記録する文字列配列で、実行時importではない。そのうち`data/remove-say-you-like-me.js`と`data/remove-code-scarlet.js`は現行mainにない。参照エラーを直す目的で新規作成したり、来歴から削除したりしない。

再生成を導入する前に、少なくとも次を確定する。

| 必要仕様 | 決める内容 |
| --- | --- |
| 入力正本 | 現行カタログを正本とするか、別入力へ移行するか。所有者と更新責任を決める |
| 上書き優先順位 | 23件の承認原稿・タイトル修正・旧補正のどれが優先か。旧文への巻き戻りを防ぐ |
| ID・除外台帳 | 全作品ID、除外8件の確定ID、削除理由、アーカイブ4件の収録維持 |
| データ仕様 | 必須/任意/空値、分類とURL、日付、掲載とリンク可否、シリーズ・関連作品の互換性 |
| 再現性 | 同じ入力から同じ出力。実行日時や推測値を混入させず、承認差分だけになること |
| 失敗時の停止 | ID重複、参照欠落、想定外の件数・本文変更で出力と公開を停止する |
| 検証・運用 | 対象フィールド差分、件数、参照、Jekyll、レスポンシブの確認と実行環境・依存版 |
| 記録保持 | 来歴・旧データ・3本の保全ブランチを維持し、生成物と非配信資料を分離する |

## 8. 公開・復元上の注意

main / rootからJekyllで公開されるため、文書のみのmain更新でもPagesのビルドが起動しうる。`README.md`と`docs`は現在`_config.yml`で配信除外されており、本書の追加はサイトの実行時依存・配信ファイルを増やさない。ただし公開リポジトリ上では閲覧できるため、機密情報を入れない。設定やHTML・JavaScriptから本書への実行時参照は追加しない。

復元は対象コミットとの差分を確認し、承認された変更としてmainへ適用する。保全ブランチを上書きしたり、履歴を強制的に巻き戻したりしない。公開後の新作を失うようなサイト全体の復元より、影響範囲に応じた変更の取り消しを検討する。

未確認事項：生成スクリプトの実体・所在と入力正本、承認原稿23件と作品IDの対応台帳、除外8作品の確定ID台帳。これらは未解決として保持する。確認前の推測による再生成・台帳補完は行わない。掲載カタログを直接更新する暫定運用も個別の作品変更承認を前提とし、生成経路の整備は別作業とする。
